# El_Inside: запуск сайта на production от начала до конца

Руководство для текущего проекта: Next.js 16, React 19, языки `/pl/` и `/en/`, Vercel и Resend. Проверено по исходникам и официальным инструкциям сервисов 1 ноября 2026 года.

**Порядок:** подготовить контент и GitHub → первый deploy Vercel → подключить домен сайта → подтвердить почтовый поддомен в Resend → создать ключ → заполнить production env → Redeploy → проверить заявки → открыть сайт клиентам.

## Что понадобится

- GitHub-аккаунт с доступом к `MahidavaAnhelina/el_inside`. Локальный `origin` уже подключён; историю с лицензией мы объединили.
- Аккаунт Vercel с доступом к этому GitHub-репозиторию.
- Аккаунт Resend.
- Собственный домен и доступ к его DNS-настройкам. Для полноценной отправки Resend нужен свой подтверждённый домен; адрес `*.vercel.app` не подходит для подтверждения в Resend, потому что доменом `vercel.app` ты не владеешь.
- Почтовый ящик подруги, куда будут приходить заявки. Подойдёт существующий Gmail, Outlook или другой рабочий ящик.

**О стоимости.** Vercel Hobby допускает только личное некоммерческое использование. Для сайта с предложением платных изделий нужен Pro или Enterprise. У Resend можно начать с бесплатного плана в пределах доступной квоты; стоимость домена и лимиты сервисов проверяй перед оплатой. [Правила Vercel](https://vercel.com/docs/limits/fair-use-guidelines), [тарифы Vercel](https://vercel.com/pricing), [тарифы Resend](https://resend.com/pricing).

Оно находится в `src/components/home.tsx` (подпись), `src/lib/pl.json` и `src/lib/en.json` (приветствие и некоторые описания). Можно использовать имя мастерицы или согласованный текст от имени бренда.

Текст о данных нужно согласовать с владелицей: кто получает обращения, как связаться по поводу данных и как долго хранятся письма/вложения. Данные, которых мы не знаем, не стоит заполнять вымышленными значениями.

Форма сейчас отправляет запрос на обсуждение. Она не принимает оплату и не подтверждает заказ автоматически. Галерея содержит примеры работ, а не гарантированное наличие.

**Результат шага:** тексты и фактические сведения готовы к публичному размещению.

## 3. Создать проект в Vercel и сделать первый deploy

1. Открой [Vercel](https://vercel.com/), выбери нужную команду/аккаунт.
2. Выбери **Add New → Project → Import Git Repository**.
3. Подключи GitHub. У тебя два аккаунта, поэтому проверь, что интеграция Vercel получила доступ именно к репозиторию `MahidavaAnhelina/el_inside`. Локальный SSH-псевдоним из `~/.ssh/config` здесь не используется: интеграция Vercel авторизуется отдельно.
4. Выбери репозиторий `el_inside`. Если его нет в списке, открой управление GitHub-интеграцией и разреши доступ к этому репозиторию нужного аккаунта.
5. Проверь настройки:

| Настройка         | Значение                                                 |
| ----------------- | -------------------------------------------------------- |
| Framework Preset  | Next.js                                                  |
| Root Directory    | Корень репозитория, обычно `./`                          |
| Node.js Version   | 24.x                                                     |
| Install Command   | `npm ci` или стандартная npm-установка Vercel            |
| Build Command     | `npm run build`                                          |
| Output Directory  | Стандартное значение Next.js; override выключен          |
| Production Branch | `main` — проверь в Git-настройках проекта после создания |

В GitHub уже загружается сама папка проекта. Поэтому Root Directory не нужно устанавливать в `el-inside` или `novaStorm`. Не настраивай `output: 'export'`: серверный `/api/orders/` должен выполняться как функция Vercel.

Для первого deploy можно ещё не задавать почтовые env. Сайт соберётся, а форма будет сообщать о временной недоступности при корректной попытке отправки. Это технический этап, а не готовый запуск.

Нажми **Deploy**, дождись **Ready** и запиши выданный проекту адрес вида `https://<имя-проекта>.vercel.app`. Это шаблон, фактический адрес выдаёт Vercel. На этом этапе `SITE_URL` ещё может указывать на localhost: до запуска это исправим и пересоберём сайт.

**Результат шага:** обе языковые главные открываются на выданном Vercel-адресе. До окончания настройки не объявляй форму рабочей.

Официально: [подключение Git к Vercel](https://vercel.com/docs/git).

## 4. Подключить домен сайта

Дальше в примерах `example.com` — твой собственный домен, а не буквальное значение для копирования.

1. В Vercel открой **Project → Settings → Domains**.
2. Добавь `example.com`.
3. При необходимости добавь `www.example.com` и настрой его перенаправление на выбранный основной домен. Например, основным будет `https://example.com`.
4. Vercel покажет DNS-записи для этого проекта. Открой DNS-панель своего регистратора и добавь предложенные A/CNAME/TXT-записи с их точными значениями.
5. Дождись подтверждения конфигурации и рабочего HTTPS. DNS обновляется не мгновенно.

Для этого проекта достаточно оставить DNS у текущего провайдера и поменять записи сайта. Не обязательно переносить nameservers в Vercel. Существующие записи почты и записи Resend, если они уже есть, сохраняй.

Проверь, что `https://example.com/pl/` и `https://example.com/en/` открываются, а второй вариант домена корректно перенаправляется на основной.

**Результат шага:** известен окончательный HTTPS-адрес сайта. Он понадобится для `SITE_URL`.

Официально: [добавление домена в Vercel](https://vercel.com/docs/domains/working-with-domains/add-a-domain).

## 5. Подтвердить домен отправителя в Resend

Раздели три настройки:

| Что это           | Пример                     | Назначение                               |
| ----------------- | -------------------------- | ---------------------------------------- |
| Адрес сайта       | `https://example.com`      | Посетители открывают сайт                |
| Адрес отправителя | `orders@mail.example.com`  | Resend отправляет письмо от этого адреса |
| Ящик получателя   | Существующая почта подруги | В него приходит заявка                   |

Для писем удобно использовать отдельный поддомен `mail.example.com` того же купленного домена. Отдельно покупать его не нужно.

1. Создай аккаунт [Resend](https://resend.com/) и подтверди email аккаунта.
2. Открой **Domains → Add Domain**.
3. Добавь `mail.example.com` и выбери доступный подходящий регион, например европейский.
4. Добавь у DNS-провайдера записи, которые выдаст Resend для **Sending**: DKIM и SPF/Return-Path. Используй имена, типы, приоритеты и значения именно из своего Resend. SPF/Return-Path может включать не только TXT, но и MX-запись на специальном поддомене.
5. В панели DNS уточни формат поля Name/Host: некоторые провайдеры автоматически дописывают `example.com`, и полное имя не нужно вводить дважды.
6. В Resend запусти проверку и дождись **Verified** для отправки.

Записи сайта из Vercel и записи отправки из Resend сосуществуют в одной DNS-зоне. Не заменяй основные MX-записи существующего почтового ящика записями Return-Path. Не добавляй несколько SPF TXT на одном DNS-имени. При конфликте сравни конкретные имена записей, а не только их тип.

`RESEND_FROM_EMAIL` затем будет `orders@mail.example.com`. Этот адрес не создаёт входящий почтовый ящик; для текущей схемы отдельный ящик на поддомене не нужен. Resend Receiving включать не требуется. Адрес Gmail/Outlook можно использовать как получателя, а свой `*.vercel.app` — как сайт, но не как подтверждаемый почтовый домен.

**Результат шага:** Resend разрешает отправку с `mail.example.com`.

Официально: [подтверждённые домены Resend](https://resend.com/docs/dashboard/domains/introduction).

## 6. Создать ключ Resend

1. В Resend открой **API Keys → Create API Key**.
2. Назови ключ, например `el-inside-production`.
3. Выбери разрешение **Sending access** и ограничь ключ подтверждённым доменом, если доступна такая настройка.
4. Сохрани значение ключа в менеджере паролей. Resend не показывает его значение повторно.

Для штатной работы не используй демонстрационного отправителя `onboarding@resend.dev`: у него ограничения на получателей. В production используй свой адрес из шага 5.

**Результат шага:** есть ключ для отправки с нужного домена. Пока его не нужно добавлять в исходный код или отправлять в чат.

Официально: [API-ключи Resend](https://resend.com/docs/dashboard/api-keys/introduction).

## 7. Добавить production env в Vercel

Открой **Project → Settings → Environment Variables**. Добавь четыре переменные для окружения **Production**:

| Имя                 | Что вписать                                           | Секрет                                                 |
| ------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| `RESEND_API_KEY`    | Полное значение ключа из Resend                       | Да                                                     |
| `RESEND_FROM_EMAIL` | `orders@mail.example.com` на подтверждённом поддомене | Нет, но используется только сервером                   |
| `ORDER_TO_EMAIL`    | Реальный почтовый ящик подруги                        | Личные контактные данные; используется только сервером |
| `SITE_URL`          | `https://example.com` — основной домен сайта          | Нет                                                    |

В таблице адреса — примеры. `SITE_URL` не должен включать `/pl/`, `/en/` или `/api/orders/`. Для адресов отправителя/получателя вводи только email, без имени, `<скобок>` и кавычек. Имя бренда в From уже добавляет сервер.

Для API-ключа выбирай тип **Secret / Sensitive**, если предлагается интерфейсом. Ни одной из этих переменных не нужен префикс `NEXT_PUBLIC_`.

Связь окружений:

- **Production** — рабочая версия из `main`, значения задаются в Vercel.
- **Preview** — тестовые версии других веток. Можно не задавать почтовые переменные; тогда отправка будет недоступна. Если нужна отправка, используй отдельный ключ и свой тестовый ящик в `ORDER_TO_EMAIL`.
- **Локально** — `.env.local` на компьютере, это отдельный файл; настройки из Dashboard сами в него не копируются. Не перезаписывай существующий файл ради production-запуска.

Для production достаточно env в Vercel; локальный файл для этого настраивать необязательно.

После сохранения открой **Deployments → нужный deployment → Redeploy**, выбери Production и дождись Ready. Убедись, что основной домен обслуживается новым deployment. Env применяются к новым развёртываниям; `SITE_URL` дополнительно участвует в сборке metadata и sitemap. Простого сохранения env недостаточно.

**Результат шага:** production использует настоящие адреса и ключ; ссылки SEO больше не указывают на localhost.

Официально: [окружения и переменные Vercel](https://vercel.com/docs/environment-variables).

## 8. Настроить ограничение частоты отправки

В коде есть honeypot, проверка Origin и ограничения данных, но распределённого счётчика запросов нет. Перед приёмом реальных заявок настрой внешний rate limit:

1. В Vercel открой проект → **Firewall → Configure → New Rule**.
2. Добавь условия: метод `POST`, путь `/api/orders` **или** `/api/orders/`. Условия пути должны объединяться через OR/список допустимых значений, а не требовать два разных пути одновременно.
3. Выбери **Rate Limit → Fixed Window**.
4. В качестве начальной настройки используй **5 запросов за 60 секунд на IP**. Это предложенная настройка для небольшой мастерской, а не обязательный лимит Vercel.
5. Действие при превышении — **Default (429)**. Не выбирай интерактивный Challenge для этого fetch-обработчика.
6. Посмотри стоимость в интерфейсе, сохрани правило, выполни **Review Changes → Publish** и проверь его события в Firewall.

По текущей документации WAF Rate Limiting доступен на всех планах; параметры и стоимость проверяй в своём аккаунте. Настройка делается отдельно от деплоя кода. Honeypot и Origin сами по себе не останавливают целевого бота.

В текущем интерфейсе формы 429 показывается как общая ошибка отправки с сохранением данных. Подожди до конца окна лимита перед повтором. Для проверки не запускай нагрузочный тест и не рассылай десятки писем.

**Результат шага:** частые запросы ограничиваются до выполнения обработчика и вызова Resend.

Официально: [WAF Rate Limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting).

## 9. Проверить путь заявки целиком

Проверяй уже на окончательном рабочем домене. Используй собственный email в поле клиента и пометку «TEST — не заказ». Держись ниже настроенного rate limit.

### Первая заявка: изделие из галереи

1. Открой `https://example.com/pl/`.
2. Нажми на изделие в галерее. Проверь, что оно выбрано в форме.
3. Выбери вариант с изменениями, опиши другой цвет или размер.
4. Приложи небольшое JPG/PNG/WEBP или PDF и добавь одну полную `https://`-ссылку.
5. Впиши имя и свой email, отправь.
6. Дождись экрана подтверждения и сохрани номер заявки.
7. В Resend → **Emails** найди отправку и проверь событие **Delivered**. Само событие Sent/успех формы ещё не гарантирует доставку.
8. В почте подруги открой письмо, при необходимости проверь «Спам». Сверь изделие, пожелания, ссылку, файл и номер заявки.
9. Нажми «Ответить»: в получателях должен быть твой email, указанный в форме, а не адрес отправителя Resend.

### Вторая заявка: новая идея на английском

Открой `/en/`, выбери **My own idea**, заполни описание и отправь вторую тестовую заявку. Проверь английские сообщения и наличие описания в письме. Повтори мобильный сценарий хотя бы до заполнения формы.

### Проверки ошибок и адресов

- Не заполненное обязательное поле не должно отправляться; описание обязательно для новой идеи и изменений.
- Файлы: не больше 5, суммарно до 3 МБ. HEIC, SVG и архивы не принимаются. Большие референсы передаются ссылками.
- После ошибки отправки данные остаются в форме.
- `/` направляет на `/pl/`; `/pl/` и `/en/` открываются напрямую.
- Дополнительные страницы `/pl/about/`, `/en/contact/` пока возвращают 404 — это ожидаемо.
- `https://example.com/sitemap.xml` содержит основной домен. В исходном HTML главных canonical/hreflang указывают на него, `lang` соответствует языку. Поиск `localhost` в metadata не должен находить локальный адрес.
- Внешний посетитель из приватного окна может открыть сайт; production не закрыт авторизацией Vercel, если сайт уже должен быть публичным.

Не удаляй рабочий ключ ради проверки ошибки на production. Сценарий недоступного провайдера проверяется автоматическими тестами или в отдельном Preview без почтовых env.

**Результат шага:** запрос с референсами дошёл из браузера до нужного ящика, а ответ из почты адресуется клиенту.

## 10. Открыть сайт клиентам

Публикуй ссылку, когда:

- [ ] Имя мастерицы и тексты на обоих языках согласованы.
- [ ] Код в GitHub соответствует проверенному deployment.
- [ ] Основной домен и HTTPS работают, второй вариант домена перенаправляется.
- [ ] В production заданы все четыре env; после их изменения выполнен Redeploy.
- [ ] Resend-домен подтверждён, ключ имеет право Sending.
- [ ] Обе контрольные заявки дошли с правильным Reply-To и вложением.
- [ ] Включён rate limit, понятны квоты и условия тарифов.
- [ ] Подруга понимает, в какой ящик приходят заявки и как подтверждать стоимость/сроки в переписке.

В текущем проекте нет автоматической оплаты, учёта статусов и копии заявок в базе. Подтверждение заказа, цена, срок и доставка согласуются в почте. Клиент не получает автоматическую копию письма: после получения заявки отвечает мастерица.

## После запуска: изменения, наблюдение, откат

### Когда меняешь код или тексты

Создай рабочую ветку, внеси изменения, выполни проверки и отправь ветку в GitHub. Vercel создаст Preview при стандартной Git-интеграции. После проверки объедини изменения в `main`; в настройках проекта `main` должна быть Production Branch. После нового production deployment проверь главную и форму.

Не отправляй секреты в коммит. Если ключ нужно поменять: создай новый, обнови Production env, сделай Redeploy, проверь одно письмо, затем отзови старый ключ. Если ключ уже скомпрометирован, отзови его сразу и восстанови отправку новым.

### Когда меняешь env, почту или домен

| Изменение                  | Что сделать                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------------- |
| Новый ящик получателя      | Изменить `ORDER_TO_EMAIL` → Redeploy → проверить доставку                                         |
| Другой адрес отправителя   | Подтвердить его домен в Resend → проверить доступ ключа → изменить `RESEND_FROM_EMAIL` → Redeploy |
| Новый API-ключ             | Изменить `RESEND_API_KEY` → Redeploy → проверить отправку                                         |
| Новый основной домен сайта | Подключить домен/HTTPS → изменить `SITE_URL` → Redeploy → проверить sitemap и форму               |
| Только Firewall-правило    | Сохранить и Publish правило в Firewall; пересборка кода для него не нужна                         |

### Что наблюдать

В первые дни проверяй папку входящих и «Спам», события доставки в Resend, расход почтовой квоты, ошибки функции `/api/orders/` в Vercel и события Firewall. Наличие красивой страницы само по себе не подтверждает работоспособность доставки.

В серверном коде специально не печатаются тексты заявок и ключи. Не добавляй их в логи ради диагностики. Мастерская отвечает за хранение переписки и вложений в своей почте; сайт не ведёт отдельную базу.

### Если обновление сломало сайт

В Vercel на карточке Production Deployment открой **Instant Rollback**, выбери доступное ранее проверенное развёртывание, сверь домены и подтверди откат. Затем исправь причину в Git и выпусти новую версию. Не применяй `git push --force` для восстановления сайта.

При откате возвращается прежняя сборка с её конфигурацией; новые env из Settings автоматически в старую сборку не попадут. Проверь совместимость её ключей и адресов. После ротации ключа безопаснее пересобрать рабочую версию с текущими env, чем возвращать сборку с отозванным ключом. [Откат Vercel](https://vercel.com/docs/instant-rollback).

## Быстрая диагностика

Код HTTP можно посмотреть в браузере: DevTools → Network → запрос `orders/` после отправки.

| Ситуация                                 | Что проверить                                                                                                     |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Vercel не видит репозиторий              | Выбран правильный GitHub-аккаунт, интеграции разрешён доступ к `el_inside`                                        |
| Build failed                             | Node 24, корень репозитория, `npm ci` и `npm run build`; первая содержательная ошибка Build Logs                  |
| Страница открывается, форма отвечает 503 | Три почтовые env существуют в Production, адреса без скобок, после сохранения был Redeploy                        |
| Ошибка 400                               | Поля, описание при изменениях/новой идее, дата, полные ссылки по строкам, типы и содержимое файлов                |
| Ошибка 403                               | Открыт окончательный домен, Origin/Host не переписываются дополнительным прокси; проверить также правила Firewall |
| Ошибка 413                               | Превышен суммарный размер файлов; заменить крупные файлы ссылками                                                 |
| Ошибка 429                               | Rate limit; подождать и посмотреть события Firewall                                                               |
| Ошибка 502                               | Ключ, право отправки, подтверждённый домен отправителя, квота и API-логи Resend                                   |
| Форма успешна, письма нет                | Правильный `ORDER_TO_EMAIL`, Delivered/Bounced в Resend, «Спам», настройки ящика                                  |
| В SEO-ссылках localhost                  | Правильный `SITE_URL` в Production и пересборка deployment                                                        |
| Почта пропала после DNS-изменений        | MX/TXT почтового провайдера сохранены, SPF не продублирован, nameservers не перенесены без переноса записей       |
