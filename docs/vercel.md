# Git, Vercel и домен

Для текущего проекта начни с [единого руководства production-запуска](production-launch.md). Репозиторий `MahidavaAnhelina/el_inside` уже подключён, история с лицензией объединена — первый раздел ниже нужен только при настройке другого репозитория.

## 0. Выбрать подходящий тариф

Бесплатный **Vercel Hobby** предназначен для личных некоммерческих проектов. Сайт, который принимает заявки на платные изделия, следует размещать на тарифе, допускающем коммерческую работу. Учтите это до запуска: связку Vercel + Resend нельзя обещать как полностью бесплатный коммерческий сайт. Самостоятельный домен также обычно оплачивается отдельно.

Проверьте актуальные [правила использования Vercel](https://vercel.com/docs/limits/fair-use-guidelines) и [тарифы](https://vercel.com/pricing). У Resend есть бесплатный план с квотой: проверьте его доступность и условия в своём аккаунте. Условия сервисов меняются.

## 1. Подключить собственный Git-репозиторий

В папке `el-inside` уже есть собственный `.git`, ветка `main` и история коммитов. Не нужно выполнять `git init` ещё раз. Репозиторий не связан с соседними проектами.

1. Создайте **пустой** репозиторий в своём GitHub/GitLab/Bitbucket без добавления README, лицензии и gitignore на стороне сервиса.
2. В терминале перейдите в `el-inside` и проверьте:

```sh
git status
git log --oneline
git remote -v
```

3. Подставьте адрес созданного репозитория:

```sh
git remote add origin https://github.com/YOUR_ACCOUNT/el-inside.git
git push -u origin main
```

Эти команды нужно выполнить самостоятельно, после создания репозитория. Убедитесь, что `.env.local` не отслеживается: `git ls-files '.env*'` должен показывать только `.env.example`. Не применяйте force push для преодоления конфликтов с уже существующим репозиторием.

## 2. Импортировать в Vercel

1. Войдите в свой аккаунт Vercel.
2. Выберите **Add New → Project**, подключите Git-провайдера и импортируйте репозиторий `el-inside`.
3. **Framework Preset:** Next.js.
4. **Root Directory:** корень репозитория (`.`), потому что репозиторий уже создан внутри папки `el-inside`.
5. **Node.js Version:** 24.x (также указано в `package.json`).
6. Оставьте стандартные команды Next.js: установка зависимостей npm и `npm run build`. Output Directory — стандартный `.next`, не `out`.
7. Не включайте static export: обработчик Resend должен работать на сервере.

Никакой отдельный backend-сервис или база данных для этого проекта не нужны. `src/app/api/orders/route.ts` автоматически становится Vercel Function.

## 3. Настроить Environment Variables

Перед Deploy добавьте переменные, либо позже откройте **Settings → Environment Variables**:

| Имя                 | Production                                        | Preview / Development                                                   |
| ------------------- | ------------------------------------------------- | ----------------------------------------------------------------------- |
| `RESEND_API_KEY`    | Ключ отправки для рабочего домена                 | Отдельный тестовый ключ или не задавать, если отправка не нужна         |
| `RESEND_FROM_EMAIL` | Адрес подтверждённого отправителя                 | Адрес тестового отправителя согласно ограничениям Resend                |
| `ORDER_TO_EMAIL`    | Почта подруги                                     | Ваша тестовая почта, чтобы не смешивать проверки с заказами             |
| `SITE_URL`          | Основной HTTPS-адрес сайта без языкового префикса | Адрес Preview, если нужен самостоятельный preview; локально — localhost |

Например, для Production: `SITE_URL=https://el-inside.vercel.app` или ваш собственный домен. Это пример, не заранее выделенный адрес: узнайте реальный адрес в Vercel. Можно задать желаемое имя проекта, а после первого deploy уточнить URL, обновить `SITE_URL` и выполнить Redeploy.

Не добавляйте кавычки вокруг значений в интерфейсе Vercel. Ключ пометьте Sensitive, если такая опция доступна. Не используйте имена `NEXT_PUBLIC_RESEND_API_KEY` и подобные.

После изменения любых env выполните **Redeploy**: они применяются к новому развёртыванию. `SITE_URL` используется при сборке статических страниц и sitemap, поэтому для него тоже нужна пересборка. Подробнее: [переменные окружения Vercel](https://vercel.com/docs/environment-variables).

## 4. Развернуть и проверить

Нажмите Deploy. После успешной сборки проверьте:

- `/` перенаправляет на `/pl/`.
- `/pl/`, `/ru/` и `/en/` работают при прямом открытии и обновлении страницы.
- Смена PL/EN/RU меняет URL; `html lang` соответствует языку.
- `/be/` и `/pl/about/` пока возвращают 404: дополнительные страницы не создавались.
- Галерея, выбор изделия, новый запрос и мобильная форма работают.
- `sitemap.xml` содержит правильный публичный домен; canonical и hreflang не ссылаются на localhost.
- Контрольная заявка доходит на нужный адрес по [гайду Resend](resend.md).

## 5. Ограничить частоту запросов до публичного запуска

В проекте есть honeypot, проверка Origin и строгая проверка данных, но нет распределённого счётчика запросов. Счётчик в памяти процесса ненадёжен для serverless, поэтому его здесь нет.

В **Project → Firewall** создайте правило rate limiting для пути `/api/orders/` и метода `POST`, с группировкой по IP. Для небольшого сайта можно начать с 5 запросов в минуту на IP и блокировки превышения; затем корректировать по реальным обращениям. Учтите также `/api/orders`, если интерфейс правил не нормализует конечный `/`.

Используйте доступные в вашем тарифе параметры и проверьте правило на тестовом развёртывании. Для fetch-формы предпочтительна блокировка с 429, а не интерактивная CAPTCHA прямо в ответе API. Если rate limiting недоступен на выбранном тарифе, перед публичным запуском потребуется другой поддерживаемый механизм: например Turnstile с серверной проверкой или внешнее хранилище счётчиков. Они не подключены в этом проекте.

Следите за квотой Resend и настройками расходов Vercel. Origin не является аутентификацией: целевой бот может отправлять запросы напрямую. Официально: [Vercel WAF Rate Limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting).

## 6. Подключить собственный домен

1. В **Settings → Domains** добавьте свой домен.
2. У регистратора создайте записи, которые предлагает Vercel. Не копируйте IP из чужих инструкций: используйте актуальные значения для своего проекта.
3. Дождитесь подтверждения DNS и HTTPS.
4. Выберите основной домен (с `www` или без), настройте перенаправление второго варианта в Vercel.
5. Поменяйте `SITE_URL` на основной HTTPS-домен и выполните Redeploy.
6. Повторите проверку `/pl/`, `/ru/`, `/en/`, sitemap и формы на новом адресе.

DNS сайта и DNS почты решают разные задачи. Сохраняйте записи Resend и существующего почтового провайдера при подключении сайта.

## 7. Дальнейшая работа

Push в `main` запускает production deployment; другие ветки обычно создают Preview. Preview можно оставить защищённым через настройки Deployment Protection. Перед переносом изменений в `main` выполняйте проверки из README.

Данные клиентов не записываются в базу сайта: основная история общения находится в почте. Для полноценного учёта заказов позже можно добавить отдельное хранилище, статусы и уведомления.
